# 브라우저 이벤트 전파와 기본 동작

학습·기록: 2026-10-21 (Asia/Seoul)
상태: 당일 학습 마무리. 버블링 출력 예측과 설명 후 두 메서드의 차이 자기 정리 확인. 자료 없는 독립 인출·새 상황 적용·지연 복습 미확인.

## 이벤트와 리스너, 버블링

이벤트는 클릭 같은 일이 일어났음을 전달하는 것이고, 리스너는 그 이벤트를 받았을 때 실행하도록 등록한 함수다. 리스너 자체가 부모로 이동하는 것은 아니다. 중첩된 요소에서 클릭 이벤트는 대상에서 처리된 뒤 조상 요소 쪽으로 전파될 수 있다. 이 흐름을 버블링이라고 한다. 부모에 별도의 클릭을 새로 만들어 내는 것으로 이해하지 않는다.

```html
<div id="parent">
  <button id="child" type="button">클릭</button>
</div>
<script>
  document.querySelector('#parent').addEventListener('click', () => {
    console.log('부모');
  });
  document.querySelector('#child').addEventListener('click', () => {
    console.log('버튼');
  });
</script>
```

예상 출력은 버튼 → 부모다. 버튼에서 click을 처리하고, 부모로 버블링하면서 부모 리스너를 실행한다. 부모 리스너를 코드에서 먼저 등록했어도 요소 간 실행 순서는 이 등록 순서로 결정되지 않는다. 세 번째 옵션을 생략한 부모 리스너는 버블링 단계에서 실행된다.

보충 설명: 이벤트 전달에는 조상에서 대상으로 내려오는 캡처링 단계도 있다. 부모에 `addEventListener('click', handler, { capture: true })`로 등록하면 캡처링 단계에서 실행된다. 이번 학습에서는 캡처링 순서 문제를 풀지 않았으므로 확인된 이해에 포함하지 않는다. 모든 종류의 이벤트가 버블링하는 것은 아니다.

## 전파와 기본 동작을 따로 생각하기

링크에는 href 주소로 이동하는 브라우저 기본 동작이 있다. 이것은 부모에 등록한 JavaScript 리스너를 실행하는 것과 다르다. `event`는 리스너가 받는 이벤트 객체이며 두 메서드를 호출할 수 있다.

```html
<div id="parent">
  <a id="link" href="/next">다음 페이지</a>
</div>
<script>
  document.querySelector('#parent').addEventListener('click', () => {
    console.log('부모');
  });
  document.querySelector('#link').addEventListener('click', (event) => {
    event.stopPropagation();
    console.log('링크');
  });
</script>
```

예상 출력은 링크 하나이며 /next로 이동한다.

1. 링크의 리스너가 실행된다.
2. stopPropagation()이 현재 이벤트의 추가 전파를 막는다.
3. 현재 함수의 다음 줄은 계속 실행되므로 링크를 출력한다.
4. 부모의 버블링 리스너는 이 클릭으로 실행되지 않는다.
5. 링크의 기본 동작은 취소하지 않았으므로 주소 이동이 이루어진다.

`stopPropagation()`은 함수의 return도 아니고 링크 이동 취소도 아니다. 보충 설명: 캡처링과 버블링 모두에서 추가 전파를 막을 수 있지만 이미 실행된 리스너를 되돌리지는 않는다. 같은 요소의 다른 리스너 실행까지 막는 메서드는 아니며, 그 차이는 이번 평가 범위 밖이다.

## preventDefault()로 바꾸면

위 링크 리스너 안의 `event.stopPropagation()` 한 줄을 다음으로 바꾼다. 두 메서드를 동시에 호출하는 예제가 아니다.

```js
event.preventDefault();
```

예상 출력은 링크 → 부모이고, 페이지는 이동하지 않는다. 링크의 리스너가 기본 동작을 취소한 뒤 링크를 출력한다. 이벤트 전파는 유지되므로 부모 리스너도 실행된다. 부모 로그가 찍힌다는 것이 링크 이동도 일어난다는 뜻은 아니다.

| 링크 리스너의 처리 | 예상 로그 | /next 이동 |
| --- | --- | --- |
| 둘 다 호출하지 않음 | 링크 → 부모 | 함 |
| stopPropagation() | 링크 | 함 |
| preventDefault() | 링크 → 부모 | 안 함 |

사용 상황을 연결하면, 중첩된 요소에서 현재 클릭이 부모의 클릭 처리까지 이어지지 않게 할 때는 전파 제어를 생각한다. 링크 이동을 취소하고 직접 처리하려는 경우에는 기본 동작 취소를 생각한다. 이 사용 상황은 보충 설명이며 학습자가 새로운 코드에 독립 적용한 근거는 아니다.

보충 설명: preventDefault()는 취소 가능한 이벤트에서 동작하며 passive 리스너에서는 기본 동작을 취소할 수 없다. 이번 예제는 일반 click 리스너를 전제로 한다. 실제 서비스에서는 링크의 기본 기능을 유지할지 먼저 판단한다.

## 실제 답변과 피드백

다음은 실제 대화의 요약이며 직접 인용이 아니다.

- 첫 버튼 문제에서 상위로 퍼지므로 버튼 → 부모라고 정확히 예측했다. 리스너가 퍼진다는 표현은 이벤트가 전파되고 각 리스너가 실행되는 것으로 다듬었다.
- stopPropagation()의 의미를 안내한 뒤 링크 예제를 제시했다. 페이지는 이동하고 부모 로그는 찍히지 않는다고 정확히 답했다.
- preventDefault()와 전파의 관계를 설명한 뒤 바꾼 결과를 물었다. 링크 → 부모 출력은 정확히 답했으나 페이지 이동 여부는 답에 포함하지 않았다. 이동하지 않는다는 점은 에이전트가 피드백으로 보충했다. 누락을 잘못된 이동 예측으로 기록하지 않는다.
- 마지막 정리에서 stopPropagation()은 버블링을 막아 상위 부모의 이벤트가 발생하지 않게 하고, preventDefault()는 브라우저 기본 수행 동작을 막는다고 설명했다. 이번 버블링 예제에서 핵심 구분은 정확하다. 부모의 이벤트 자체를 없애는 것이 아니라 현재 이벤트의 추가 전파를 막는다는 표현과 캡처링에서도 사용할 수 있다는 점을 마지막 피드백으로 보완했다.

마지막에는 앞선 설명을 보지 않고 정리하도록 안내했지만 실제 참고 여부는 미확인이다. 설명 직후 자기 정리로 기록하며 장기 숙달로 확정하지 않는다. 뚜렷한 핵심 오개념은 확인되지 않았고 용어를 보완했다. 정식 복습 점수나 오류 횟수는 부여하지 않는다.

## 예제의 한계와 다음 확인

예제는 일반 브라우저 문서에서 클릭하는 상황이며 /next라는 이동 대상 경로를 가정한다. 이번 학습에서 브라우저 실행 검증은 하지 않았다. 모든 출력과 이동은 예상 결과다. 캡처링, 같은 요소의 여러 리스너, 이벤트 위임, target/currentTarget, 폼 제출에의 독립 적용은 확인하지 않았다.

첫 복습 예정은 2026-10-22다. 버블링 순서와 전파 중단·기본 동작 취소의 차이를 이미 배운 범위에서 확인한다. 다음 새 주제는 HTTP 요청과 응답·상태 코드로, 링크 이동 이후 서버와 주고받는 내용을 연결한다.
