# State·Ref와 비동기 요청

최초 기록일: 2026-10-15 · 추가 학습: 2026-10-21 (Asia/Seoul)
상태: 렌더별 state·ref 당일 학습 마무리. 설명 후 자기 정리와 짧은 변형 예측 확인, 자료 없이 독립 인출·지연 복습 미확인.

## 출발한 문제

검색어를 `리` → `리액` → `리액트`로 빠르게 변경했다. 이전 요청이 가장 늦게 응답하면 최신 검색 결과를 덮을 수 있다.
요청 순서와 응답 순서는 같다고 보장할 수 없다. 이 원인은 학습자가 처음부터 정확히 설명했다.

## 핵심 개념

state 값은 각 렌더에서 전달받은 스냅샷이다. setter는 다음 렌더의 업데이트를 요청하며, 이미 실행 중인 함수가 참조하는 그 렌더의 변수를 교체하지 않는다. `await` 이후에도 같은 렌더의 값을 참조한다. [React: State as a Snapshot](https://react.dev/learn/state-as-a-snapshot)

ref는 같은 컴포넌트 인스턴스의 렌더 사이에 같은 객체를 유지한다. `.current`는 변경할 수 있고, 그 변경 자체는 리렌더링을 요청하지 않는다. ref도 클로저의 참조 대상이지만, 응답 시점에 객체의 속성을 다시 읽을 수 있다. [React: Referencing Values with Refs](https://react.dev/learn/referencing-values-with-refs)

## 대화에서 바로잡은 생각

아래는 질문과 답변의 요약이다.

| 처음의 생각·질문 | 정리 |
| --- | --- |
| setter 다음 줄에서 state를 읽으면 새 값 아닌가? | 기존 함수는 해당 렌더의 값을 참조한다. 단순히 기다리는 시간의 문제가 아니다. |
| 함수형 업데이트를 쓰면 현재 함수의 state도 최신인가? | `prev => prev + 1`은 다음 상태 계산에 쓰인다. 현재 함수의 변수를 교체하지 않는다. |
| ref도 클로저 문제를 피할 수 없지 않나? | 클로저가 없어지는 것은 아니다. 같은 객체의 속성을 나중에 읽는다는 점이 다르다. |
| `++ref.current`는 언제 값을 올리나? | 그 표현식에서 속성을 먼저 1 증가시키고 증가한 값을 반환한다. |
| ref는 리렌더링되어도 변하지 않는 값인가? | 값은 바뀔 수 있다. 렌더 사이에 유지되는 저장 공간이다. state도 렌더 사이에 유지된다. |

## 요청 번호로 이전 응답 무시하기

컴포넌트 내부 발췌다. `fetchResults`는 비동기 조회 함수, `setResults`는 결과 state의 setter라고 가정한다.

```jsx
const latestRequestId = useRef(0);

async function search(query) {
  latestRequestId.current += 1;
  const requestId = latestRequestId.current;

  const results = await fetchResults(query);

  if (requestId === latestRequestId.current) {
    setResults(results);
  }
}
```

각 호출의 `requestId`는 고정된 숫자이고, `latestRequestId.current`는 여러 호출이 공유하는 최신 번호다.

| 순서 | 상황 | 첫 호출의 번호 | 공유하는 최신 번호 |
| --- | --- | --- | --- |
| 1 | 첫 호출 시작 | 1 | 1 |
| 2 | 두 번째 호출 시작 | 1 | 2 |
| 3 | 첫 호출 응답 도착 | 1 | 2 |

세 번째 단계에서 비교가 거짓이므로 첫 응답을 반영하지 않는다.

## 선택 기준과 예제의 범위

검색 결과처럼 화면에 반영할 정보는 state로 관리한다. 요청 번호처럼 이벤트 처리에 필요하지만 변경 자체가 화면 갱신을 요구하지 않는 정보는 ref에 보관할 수 있다.

보충 설명: 이 예제는 마지막으로 시작한 요청의 성공 결과만 반영한다. 이전 네트워크 요청을 취소하지 않으며, 최신 요청 실패 시 이전 성공 결과를 대신 반영하지도 않는다. 오류·로딩·언마운트 처리는 이후 학습 대상이다. 교육용 발췌이며 실행 검증은 하지 않았다.

## 2026-10-21: 렌더별 환경과 state 스냅샷

렌더링은 React가 컴포넌트 함수를 호출해 화면을 계산하는 과정이다. 함수 호출마다 지역 환경이 생기며, useState가 반환한 count는 해당 렌더의 상태 값이다. setCount(1)은 다음 상태 업데이트를 요청한다. 이미 실행한 렌더의 지역 변수에 count = 1을 대입하는 동작이 아니다. 이전에 만든 함수는 자신의 정의 환경에 연결되어 있으므로 나중에 실행해도 이전 렌더의 count를 읽는다. 클로저가 값을 무조건 복사해 고정하기 때문이 아니다.

다음은 컴포넌트 내부 발췌이며 handleClick이 버튼에 연결되어 있다고 가정한다.

```jsx
const [count, setCount] = useState(0);

function handleClick() {
  setTimeout(() => {
    console.log(count);
  }, 3000);
  setCount(1);
}
```

첫 화면에서 한 번 누르면 예상 출력은 0이다.

1. count가 0인 렌더에서 만든 handleClick을 호출한다.
2. 그 환경의 count를 읽는 타이머 콜백을 등록한다.
3. setCount(1)이 업데이트를 요청한다.
4. React가 다시 컴포넌트를 호출하면 그 렌더의 count는 1이며 화면에도 반영된다.
5. 앞서 등록된 콜백은 여전히 이전 환경의 count인 0을 읽는다.

화면에 1이 반영된 뒤 다시 클릭하면 새 렌더의 핸들러가 타이머를 등록하므로 그 타이머는 1을 출력한다. 기다리는 시간을 늘리는 것만으로 기존 콜백이 새 렌더의 변수로 연결되지는 않는다.

최초 코드 없는 질문에 학습자는 1이라고 답했지만, 코드를 본 뒤에는 처음부터 0으로 답했을 것이라고 밝혔고 재클릭 상황을 명확히 확인했다. 질문 전달의 모호성을 인정했으며 이 최초 응답은 state 오개념의 확정 근거나 평가 점수로 사용하지 않는다.

## ref 객체가 유지된다는 뜻

useRef(0)은 current 속성의 초기값이 숫자 0인 객체를 반환한다. 숫자가 참조형으로 바뀌는 것은 아니다. 같은 컴포넌트가 유지되는 동안 다음 렌더의 useRef도 같은 ref 객체를 반환한다. 지역 변수는 렌더마다 생겨도 그 변수들이 가리키는 객체는 같다.

```text
이전 렌더의 countRef ──┐
                      ├──→ 같은 객체 { current: 1 }
다음 렌더의 countRef ──┘
```

동일한 객체라는 말은 속성이 불변이라는 뜻이 아니다. current를 바꾸면 그 객체를 참조하는 함수는 나중에 속성을 읽을 때 변경된 값을 얻는다.

```jsx
const [count, setCount] = useState(0);
const countRef = useRef(0);

function handleClick() {
  setTimeout(() => {
    console.log(count, countRef.current);
  }, 3000);
  setCount(1);
  countRef.current = 1;
}
```

처음 한 번 클릭했을 때 예상 출력은 0, 1이다. 타이머는 이전 렌더의 count인 0을 읽지만, countRef는 동일한 객체를 가리킨다. 이벤트 핸들러에서 그 객체의 current를 1로 바꿨으므로 콜백 실행 시 읽는 속성은 1이다. ref 변경 자체는 렌더링을 요청하지 않는다. 이 예제의 화면 갱신은 state setter로 일어난다.

학습자는 처음 0, 0으로 예측했다. 설명 이후 객체 참조와 속성 읽기로 이유를 정리했다. 문자열 변수와 같아야 하는지 추가로 질문했고 다음 일반 JavaScript 예제로 보완했다.

```js
const text = "처음";
const box = { current: "처음" };
const savedText = text;
const savedBox = box;
box.current = "변경";
console.log(savedText);        // 예상: "처음"
console.log(savedBox.current); // 예상: "변경"
```

savedText에는 문자열 값이 저장된다. savedBox와 box에는 같은 객체를 가리키는 참조가 저장되므로 어느 쪽으로 속성을 읽어도 변경이 보인다. 학습자는 객체의 참조값 또는 주소값을 저장한다는 뜻이라고 확인했다. 주소 비유는 가능하지만 JavaScript 코드가 실제 메모리 주소를 직접 다루는 것은 아니라는 점은 에이전트의 보충 설명이다. 초기 표현만으로 숫자를 참조형으로 오해했다고 단정하지 않는다.

## 속성을 미리 꺼낸 값과 나중에 읽는 값

```jsx
function handleClick() {
  const saved = countRef.current; // 첫 클릭 시 숫자 0
  setTimeout(() => {
    console.log(saved, countRef.current);
  }, 3000);
  countRef.current = 1;
}
```

countRef의 초기 current가 0이고 처음 한 번 클릭했다고 가정한다. saved 초기화 시점에 숫자 0을 읽어 저장한다. 이후 객체 속성을 바꿔도 saved와의 자동 연결은 없으므로 예상 출력은 0, 1이다. 학습자는 앞선 설명 후 이 변형의 출력을 정확히 예측했다.

반대로 const savedRef = countRef라면 ref 객체 자체의 참조를 저장하므로 savedRef.current도 변경된 1을 읽는다. 무엇을 저장했는지와 언제 속성을 읽는지가 중요하다. 이 설명은 current가 숫자인 예제이며, current 자체에 객체가 담겨 있으면 그 속성을 꺼낸 변수도 해당 객체의 참조를 갖는다. 마지막 경우는 보충 설명이며 독립 적용은 확인하지 않았다.

## 사용 기준과 설명의 한계

화면에 표시되는 숫자나 검색 결과처럼 변경 시 화면 계산이 필요한 정보는 state로 관리한다. 타이머 ID나 최신 요청 번호처럼 렌더 사이에 보관하되 변경 자체가 화면 갱신을 요구하지 않는 정보는 ref에 둘 수 있다. state도 상태를 유지하므로 단순히 유지 여부만으로 구분하지 않는다.

학습자는 화면 숫자에는 state가 적절하고 컴포넌트와 자식이 다시 렌더링되기 때문이라고 답했다. 자식 렌더링은 메모이제이션 등으로 생략될 수 있으며 렌더링과 실제 DOM 변경은 다르다는 내용은 피드백으로 보충했다. 이 세부 예외를 학습자가 독립 설명했다고 기록하지 않는다.

학습자는 ref를 렌더마다 새로 계산하지 않고 유지하며 변경 시 렌더링이 필요 없는 값을 담는 용도로 설명했다. 정확한 표현은 같은 객체가 유지된다는 것이다. 보충 설명: useRef(expensiveCalculation()) 형태의 인자 표현식은 컴포넌트 호출 시 평가될 수 있다. useRef는 임의의 계산을 자동으로 생략하는 도구가 아니다. current는 직접 갱신한 값이며 state와 자동 동기화되지 않는다. 이번 예제의 읽기·쓰기는 이벤트 핸들러와 타이머 안에서 수행한다. 일반적으로 렌더 도중 ref를 읽거나 쓰는 방식은 피한다.

이 문서의 React 및 일반 JavaScript 예제는 예상 결과로 설명했으며 이번 세션에서 실행 검증하지 않았다. 컴포넌트 재마운트, Effect 정리, 요청 취소, 실제 기능 구현은 이번 확인 범위 밖이다.

## 최종 정리와 확인 범위

아래는 2026-10-21 사용자 답변의 요약이며 직접 인용이 아니다.

- 이전 타이머는 만들어진 렌더의 변수를 읽으므로 이전 state를 읽는다.
- ref는 객체를 참조하므로 속성을 읽는 시점에 변경된 값을 얻을 수 있다.
- 화면에 표시할 값은 state가 적절하며, 변경 자체에 렌더링이 필요 없는 저장 값에는 ref가 적절하다.

자료 없이 최종 설명하도록 안내했으나 실제 참고 여부는 미확인이다. 사용 기준 답변 후 설명을 보완하고 남은 이유를 다시 질문해 최종 답변을 받았다. 따라서 설명 후 자기 정리 근거로 기록하며 완전히 도움 없는 종합 인출이나 장기 숙달로 확정하지 않는다. 짧은 saved 변형 예측은 정답이었으나 실제 기능의 독립 구현은 확인하지 않았다. 정식 복습 점수와 오류 횟수는 추가하지 않는다.

첫 복습 예정일은 2026-10-22다. 렌더별 state, 객체 참조와 속성값 저장, 화면 갱신 기준을 배운 범위에서 다시 확인한다. 다음 새 학습은 영역 균형을 위해 HTML의 button·a 의미와 키보드 접근성으로 진행한다.
